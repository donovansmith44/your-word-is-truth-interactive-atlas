# Bible Atlas

An explorable Bible atlas: a KJV reader alongside a `/world` map with a time
slider, narrative arrows, and cross-references. Rust API (`server/`) + Blazor
WebAssembly client (`client/`). Everything the app serves out of
`data/compiled/` is generated by `atlas-etl` from open datasets — nothing in
there is hand-typed at runtime.

## Prerequisites

- **Rust** (stable). On Windows the default host toolchain is
  `x86_64-pc-windows-gnu`, which needs a one-time setup step before the
  first `cargo build`/`cargo test` in `server/`: run `server/setup-toolchain.ps1`.
  windows-gnu's bundled `dlltool` shells out to a GNU assembler this kind of
  machine doesn't have by design; the script provisions a self-contained
  LLVM `dlltool` instead (copied to
  `%USERPROFILE%\.cargo\atlas-tools\llvm-dlltool.exe`). `server/.cargo/config.toml`
  points `-C dlltool=` at that exact path as a **literal, user-specific
  path** (cargo's `config.toml` doesn't expand env vars inside `rustflags`)
  — if your Windows username isn't the one already baked into that file,
  edit the path after running the script. The script is idempotent, safe to
  re-run any time.
- **.NET 10 SDK** (`dotnet --version` → `10.0.x`) — the Blazor WebAssembly
  client and its xunit tests.
- **Node 24** + npm — the Playwright UX property suite in `tests/ux/`.

Every fresh PowerShell session needs Rust and dotnet on `PATH` before running
anything under `server/` or `client/`:

```powershell
$env:Path = "$env:Path;$env:LOCALAPPDATA\Microsoft\dotnet;$env:USERPROFILE\.cargo\bin"
$env:DOTNET_ROOT = "$env:LOCALAPPDATA\Microsoft\dotnet"
```

## Data pipeline

`data/compiled/` is gitignored — nothing in it is committed; it's
regenerated from `data/raw/` (fetched) + `data/curated/` (hand-authored TOML)
by `atlas-etl`:

```powershell
# 1. Fetch the raw open datasets into data/raw/ (idempotent -- skips files
#    it already has; see data/raw/README.md for what each one is and why).
.\data\fetch-raw.ps1

# 2. Compile data/raw/ + data/curated/ -> data/compiled/*.json
cd server
cargo run -p atlas-etl
```

`atlas-etl` prints a report (file counts, per-narrative leg counts, KJV/
Theographic coverage percentages, warnings) and exits non-zero on any
validation failure — unknown place ids referenced by an event, a dangling
narrative leg, a non-canonical verse ref, an era gap/overlap, a duplicate id,
non-chronological narrative legs, etc. (see `server/atlas-etl/src/validate.rs`
for the full list). A clean run currently compiles 66 books, 1,375 places,
552 events, **13 narratives**, 10 eras, 31,102 KJV verses, and 29,364
cross-reference source verses, with 0 warnings.

## Dev loop

Two processes, two ports — run each from the repo root in its own terminal:

```powershell
# Terminal 1 -- the API
cd server
cargo run -p atlas-server -- --data-dir ../data/compiled --port 8000

# Terminal 2 -- the Blazor client's dev server
dotnet run --project client --launch-profile http   # http://localhost:5000
```

The client's `wwwroot/appsettings.Development.json` points `ApiBase` at
`http://localhost:8000`; the dev server doesn't proxy API calls, so the
server's permissive CORS (`server/atlas-server/src/app.rs`) is what makes
the client's cross-origin `fetch` calls from `:5000` to `:8000` work in dev.

**Port hygiene**: free 8000/5000 by looking up the PID that actually owns the
port (e.g. `Get-NetTCPConnection -LocalPort 8000`) and stopping that PID —
never by killing a process by name. A user's own demo/dev server on some
other port (e.g. 8080) must never be touched.

## Tests

```powershell
# Rust workspace (from server/)
cargo test --workspace
# -> 102 tests, 0 failed, ~19s

# Blazor xunit (from repo root)
dotnet test client.Tests
# -> 15 tests, 0 failed, ~4s

# Playwright UX property suite (from tests/ux/) -- auto-starts AND stops
# both dev servers itself, via playwright.config.ts's webServer entries
cd tests/ux
npx playwright test
# -> 36 tests, 0 failed, ~1.5m
```

`dotnet build client` should come back 0 warnings, 0 errors.

**Never run `dotnet build`/`dotnet test` on the client while its own dev
server (`dotnet run --project client`) is serving** — it corrupts the
already-served WASM output out from under the running server (a proven flake
source, not a theoretical one).

### Deep exhaustive run (two-tier)

The UX suite's property-based tests all share one `FC_NUM_RUNS` env knob
(`tests/ux/lib/fc.ts`: `RUNS_API` defaults to 150, `RUNS_UI` to 20, but
setting `FC_NUM_RUNS` overrides *both* to the same number). Running the
*entire* suite — including every browser-driven spec (map rendering, slider
drags, popovers, each doing real page loads) — at a single high count meant
for the API-only properties would take hours: a browser property normally
run 20 times a run would suddenly run 500 times, each iteration paying a
real WASM page-load cost. So the deep run is split into two tiers, each
using the shared knob at a level appropriate to what it's driving:

```powershell
cd tests/ux

# Tier 1: the API-only property tests, no browser, FC_NUM_RUNS=500
$env:FC_NUM_RUNS = 500
npx playwright test api-

# Tier 2: the full suite (including every browser-driven spec), FC_NUM_RUNS=60
$env:FC_NUM_RUNS = 60
npx playwright test

Remove-Item Env:\FC_NUM_RUNS
```

Real results from this repo (release-mode API, same machine, back to back):

| Run | Command | Tests | Result | Wall time |
|---|---|---|---|---|
| Default | `npx playwright test` | 36 | 0 failed | ~1.5m |
| Deep tier 1 | `FC_NUM_RUNS=500`, `api-` only | 11 | 0 failed | ~24s |
| Deep tier 2 | `FC_NUM_RUNS=60`, full suite | 36 | 0 failed | ~3.7m |

Tier 1 is *faster* in wall time than the plain default run despite running
each API property 3.3x as many times (500 vs. the default 150) — it skips
every browser-driven spec entirely, and pure API+validation iterations are
cheap (sub-millisecond each once the assertions themselves are cheap; see
the `ok()` note below). Tier 2's slowest single test is WORLD-1
(`world-map.spec.ts`), which does a full page reload per iteration — its
own cost scales close to linearly with `FC_NUM_RUNS` (measured ~42s at the
default 20 runs, ~2.1m at 60), which is why `playwright.config.ts`'s
per-test `timeout` has real margin above that (240s) rather than being
tuned to the exact figure.

**Note on `api-scene.spec.ts`**: its two window-scene properties
(`SCENE-1/2 + ARROW-1..7`, `SCENE-3`) validate every place/event/arrow in
whatever scene a random window produces — proportional to real scene size,
up to ~200 places and ~90 arrows for a wide window. Earlier in this
dataset's growth that per-iteration validation used Playwright's `expect()`
for every individual check (thousands of calls per iteration at the largest
window sizes); `expect()`'s own per-call bookkeeping (stack capture, etc.)
turned out to dominate the wall time at high `FC_NUM_RUNS`, to the point of
not finishing at all at 500 runs. Both properties now use a small local
`ok(cond, msg)` throw-helper instead (identical pass/fail semantics, no
tracked-assertion overhead) — confirmed via a standalone Node reproduction
outside Playwright entirely that the underlying logic was always correct
and fast (500 iterations in well under a second); only the assertion
mechanism was the bottleneck.

## Publish path

Builds a single self-contained deployment: one `atlas-server` binary serving
both the API and the published Blazor client, same-origin.

```powershell
dotnet publish client -c Release -o publish
cd server
cargo run -p atlas-server -- --data-dir ../data/compiled --static-dir ../publish/wwwroot
```

Browse `http://localhost:8000/`. The published `wwwroot` carries no plain
`appsettings.json` (only `appsettings.Development.json`, which only loads
under `ASPNETCORE_ENVIRONMENT=Development`), so the client's `ApiBase`
defaults to empty in this configuration — same-origin `fetch("/api/...")`
calls, no CORS round trip needed. SPA deep links (`/world?from=...&to=...`,
`/read/EXO/14`, any client-side route) fall back to `index.html` with a real
HTTP `200`, not tower-http's native `404` for its `not_found_service`
single-page-app idiom — see `app.rs`'s `build()` doc comment and the
`static_dir_serves_files_api_still_wins_and_falls_back_to_index_for_spa_routes`
test in `server/atlas-server/tests/api.rs` for why that fix exists and how
it's pinned.

`publish/` is gitignored — it's a build artifact, not source; regenerate it,
never commit it.
